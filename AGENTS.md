# Правила проекта

## Общие принципы

- Использовать строгую типизацию TypeScript; не применять `any` без документированной причины.
- Предпочитать небольшие, переиспользуемые функции и компоненты с одной ответственностью.
- Давать понятные имена сущностям; избегать неочевидных сокращений.
- Перед добавлением зависимости проверять, нельзя ли решить задачу средствами текущего стека.
- Не коммитить секреты, локальные настройки, `node_modules` и артефакты сборки.

## Архитектура

- Соблюдать чистый Feature-Sliced Design: `app`, `pages`, `widgets`, `features`, `entities`, `shared`.
- Слои могут импортировать только нижележащие слои; обратные и циклические зависимости запрещены.
- Бизнес-логику размещать в соответствующем слое, а не в страницах и UI-компонентах.
- Общие UI-компоненты, типы и утилиты размещать в `shared`.
- Публичный API слайса оформлять через index-файлы; не импортировать внутренние файлы соседнего слайса напрямую.

## React и состояние

- Использовать функциональные компоненты и хуки.
- Соблюдать правила хуков и не хранить производные данные в состоянии без необходимости.
- Для списков использовать стабильные ключи, связанные с сущностью, а не индекс массива.
- Разделять серверное, глобальное и локальное состояние; не поднимать состояние выше необходимого.
- Не смешивать форматирование, валидацию и бизнес-правила непосредственно в JSX.

## Данные и тестирование

- Явно моделировать доходы, расходы, категории и периоды через TypeScript-типы.
- Валютные значения хранить в безопасном для вычислений формате и форматировать только на границе UI.
- Фильтрацию и расчёты делать детерминированными чистыми функциями.
- Добавлять тесты для расчётов, фильтрации и критичных пользовательских сценариев.
- Перед завершением изменений запускать `npm run lint` и `npm run build`.

## Стиль

- Следовать настройкам ESLint и форматированию проекта.
- Предпочитать доступные HTML-элементы и добавлять ARIA-атрибуты только там, где они нужны.
- Не использовать `console.log` в production-коде.
